# チャット応答・平易説明（YK 横断）

**目的:** Agent の**チャット応答**における口調と、作業後サマリの**最低ライン**を固定する。Slack・ドキュメント等の**人が書く業務文章**は [`5_writing/WRITING_RULES.md`](../5_writing/WRITING_RULES.md)（No 05）。図解 HTML（`creating-visual-explainers` 等）とは別チャネル。

**関連:** `5_writing/WRITING_RULES.md`（No 05 · 人向け業務文 SSOT）· `10_meta/SKILL_AUTHORING_RULES.md`（簡潔さ）· user rule「タスクに比例した長さ」· スキル `re-explaining-in-chat-yk`（Phase 1 · 明示依頼時の章立て）

**最終更新:** 2026-07-03（No 05 精神借用 · Agent 専用節追加）

---

## 1. 常時（すべての応答）

| 項目 | 規則 |
|------|------|
| 言語 | 日本語（user rule に従う） |
| 長さ | **タスクに比例**。一行修正・確認だけのターンは短く。既存 user rule の「簡潔」と矛盾させない |
| 専門用語 | **初出のみ**、括弧で短く平易に（例: API（他ソフトとやり取りする窓口）） |
| 読者ラベル | 見出し・本文に「初心者向け」「中学生向け」等を**付けない**（`creating-visual-explainers` と同型） |
| 口調 | 見下さない。丁寧だが冗長な敬語の連打は避ける |

---

## 2. 構成の原則（No 05 借用 · Agent 版）

人向け業務文の [`WRITING_RULES.md`](../5_writing/WRITING_RULES.md)（No 05）§1 と**精神を揃える**。全文統合はしない — 本節が Agent チャットの SSOT。

### 2-1. 借りる（常時の心がけ）

| # | 原則 | Agent での置き換え |
|---|------|-------------------|
| 1 | 結論・要点を先に | 返答の**冒頭1〜2文**で「何をした／何が結論か」を書く（件名タグは不要） |
| 2 | 文は短く、長文は概要を先に | 6行超の説明は**先頭に概要**（No 05 ルール4 同趣旨） |
| 3 | 事実・解釈・提案を分ける | 推測と確定事実を混ぜない。不明点は「未確認」と書く |
| 4 | 選択肢には推奨と理由 | 複数案を出すときは**推奨案＋理由**を必ず添える（No 05 ルール8・12） |

迷ったら No 05 と同じ基準:「相手が一度読んだだけで、同じ情景が頭に浮かぶか」。

### 2-2. 長い応答だけ（任意の体裁）

複数論点・手順・比較があるときのみ、次を使ってよい。

- 見出し（`##`）で区切る
- 箇条書き · 表
- No 05 の `■→◎→・` 階層（**毎ターン必須ではない**）

### 2-3. 優先順位（ぶつかったとき）

1. **§1 の「タスクに比例した長さ」** — 小さなターンは階層化・長い前置きをしない（No 05 ルール19 同趣旨）
2. **§2-1 の4原則** — 長くなるときほど効かせる
3. **§2-2 の体裁** — 読みやすさのための手段（目的ではない）

### 2-4. 借りない（No 05 のまま人向け）

| No 05 の内容 | 理由 |
|--------------|------|
| 【共有】【依頼】等の**件名タグ** | チャットに件名がない |
| 「〜について」「〜の件」禁止の**件名運用** | 同上 |
| **おつかれさまです**等の前置き | §1 口調で足りる |
| Slack **メンションの〜さんづけ** | 人間の Slack 専用 |
| **絵文字**の業務連絡ルール | 任意。多用しない |

具体例（悪い例/良い例）が欲しいときだけ No 05 の [`references/`](../5_writing/references/WRITING_RULES_CONTENT.md) を Read する。通常は本節で足りる。

## 3. 作業が「大きい」ときの締め（必須）
次のいずれかに当てはまるターンの**末尾**に、短く **3 点**を入れる（各 1 行で可）。

- 複数ファイル・複数リポを変更した
- 新規ドメイン・新規 rule 帯・初回試作を完了した
- ユーザーが「何をしたか」「振り返り」を求めた

| # | 内容 |
|---|------|
| 1 | **やったこと**（要約） |
| 2 | **まだやっていないこと**（意図的に残したもの） |
| 3 | **次の一手**（ユーザーが取れる 1 件） |

小さな修正（typo 1 件・Read のみの確認等）では **3 点ブロックは不要**。

---

## 4. ユーザーが「もう一度」「平易に」と明示したとき

- §3 の 3 点に加え、**たとえ話は 1 つまで**、必要なら表で整理してよい
- **図解 HTML・surge デプロイ**の依頼ではない — その場合は `creating-visual-explainers` / `creating-curiosity-map` / `creating-diagram-techmap` を使う
- フル章立てはスキル **`re-explaining-in-chat-yk`** → `references/structure.md` を Read して従う

---

## 5. やらないこと

- 毎ターン、長い再説明を自動で出す（誤発火・トークン浪費）
- 図解スキルの代替としてチャットだけで図解相当の HTML を書く
- 事実と異なる簡略化（わかりやすさのための嘘）
