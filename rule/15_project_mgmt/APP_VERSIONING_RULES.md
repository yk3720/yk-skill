# アプリバージョン管理規則
## App Versioning — SemVer 運用 + ビルド日時表示 v1

**用途:** `yk-application` 配下の自作アプリ(デスクトップ/Web/CLI問わず・言語不問)で、バージョン番号とビルド日時をどう管理・表示するかの横断 SSOT。
**ステータス:** active(L1)
**関連:** `15_project_mgmt/APP_PROJECT_RULES.md`(個人アプリ全般)・`15_project_mgmt/YK_APPLICATION_RULES.md`(独立リポ移行・置き場)・Tauri固有の実装詳細は L0 `tauri2-dev-yk.mdc`
**実例:** manual-studio(詳細は末尾§6)

**最終更新:** 2026-10-01(§4に表示場所の原則を追記 — 起動画面だけでなくメイン画面にも目立たせず表示。manual-studioの実機テストで「起動画面まで戻らず確認したい」という要望から判明)

---

## 1. 適用対象

バージョン番号を持つ個人アプリ(デスクトップ・Web・CLI、言語不問)。使い捨てスクリプト・単発ツールには強制しない — 「継続的に機能追加・バグ修正が入る」フェーズに入ったら適用する(`YK_APPLICATION_RULES.md` §3「独立リポジトリ管理への移行基準」と同じ目安)。

---

## 2. SemVer 運用

| 項目 | 方針 |
|------|------|
| 形式 | `MAJOR.MINOR.PATCH`(`0.x.y`のまま運用。`1.0.0`移行は「安定して使い始めた」とユーザーが判断した時点) |
| MINOR | ロードマップの機能追加ごとに+1 |
| PATCH | **修正を1件加えるたびに必ず+1**(実機テスト・レビューで見つかった不具合修正を含む。「バグ修正のみのコミット」という曖昧な基準にしない) |
| 桁数 | **3桁のまま固定**。PATCHは上限なく増やせるため、細かい修正が多くても4桁化しない(4桁化すると各マニフェストファイルが要求する厳密なSemVer形式と衝突し、`version`フィールドにそのまま書けず表示用の別値管理が必要になって実装が複雑化する) |

**MUST:** コード修正を伴うコミットでは、**同じコミットで**バージョンを上げる(「次のコミットで上げる」は許容しない — §5のフックは直前1コミットとの比較のみを行うため、別コミットへ先送りする運用は機械的強制と両立しない)。上げ忘れに気づいたら、そのコミットに追いコミットするか`--amend`する。

---

## 3. バージョン管理箇所(複数マニフェストの同期)

Tauri(`Cargo.toml`+`tauri.conf.json`+`package.json`)のように、1アプリに複数のバージョンフィールドが分散するスタックがある。自動同期の公式手段が無い場合、**手動同期で良い**(個人アプリは更新頻度が低いため。§5のフックで値の一致も機械的に二重チェックされる)が、以下を徹底する。

| MUST | 理由 |
|------|------|
| 全マニフェストを**同一コミットで**同じ値に揃える | 値がズレるとどれが正か分からなくなる |
| アプリの `技術方針.md` 等に管理箇所(ファイルパス一覧)を列挙する | 次回セッションで上げ忘れるファイルを作らない |

## 4. ビルド日時の表示

バージョン番号だけでは「いつビルドしたものか」が分からず、同日に複数回PATCHを上げた場合に区別しにくい。**年月日時分秒(秒まで)** を表示する。

**表示場所の原則:** 起動画面・aboutダイアログだけでなく、**普段作業するメイン画面にも**表示する(実機テスト中に不具合を見つけた際、起動画面まで戻らず今のバージョンを確認できるようにするため)。ただし常時目に入ると鬱陶しいため、**目立たせすぎない**(画面の隅に小さく・muted色で配置し、主要なUI要素と並べて強調しない)。

| スタック | 実装パターン |
|----------|-------------|
| Vite(Tauri等) | `vite.config.ts`の`define`でビルド実行時刻を文字列定数として埋め込む(例: `__BUILD_TIME__`)。`vite-env.d.ts`に`declare const`で型宣言し、UI側で`v{version} ({__BUILD_TIME__})`のように並べて表示 |
| Python(PyInstaller等) | **ビルドスクリプト実行時**に`datetime.now()`で生成した文字列を、ソース中の定数ファイル(例: `_build_info.py`の`BUILD_TIME = "..."`)へ書き込んでおき、`--version`ハンドラはその**定数を読んで表示するだけ**にする。`--version`のコード内で直接`datetime.now()`を呼ぶのは**不可**(実行のたびに現在時刻が出て「ビルド時刻」ではなくなり、下記の注意と矛盾する) |
| その他 | ビルド工程で生成される任意の定数ファイル・環境変数に埋め込む方式で代替可。ビルド手段を持たないスクリプト類は対象外 |

**注意:** これは**ソースコードの変更日時**ではなく**ビルドを実行した時刻**。ビルドし直さない限り更新されない(watch/HMRでの自動反映ではない点に注意)。**本節の要件は§5のpre-commitフックでは検証されない**(表示の有無・形式はコードレビュー時の目視確認に留める)。

---

## 5. フックでの機械的強制

ルールを文書化するだけでは「AIが覚えている間だけ」しか守られず、別セッション・人間が直接commitする場合に抜ける。**git pre-commitフックで機械的にブロックする**。

**MUST(継続開発フェーズのアプリ):** `YK_APPLICATION_RULES.md` §2「開発中」フェーズ以降(§1の適用対象に入った)アプリは、本節のフックを導入する。**実験段階(§2「初期・実験」)のアプリは任意**(導入しなくてもルール違反にならない)。フェーズ移行時のチェックリストに本節の導入確認を含める(`YK_APPLICATION_RULES.md` §2参照)。

| 項目 | 方針 |
|------|------|
| チェック内容 | ①ステージに`src/`等のソース変更があるか(パスの決め方は下記) ②あるなら、全バージョンマニフェストが**前回コミットと異なる値**になっているか ③複数マニフェストがある場合は**値が一致しているか** |
| ソース判定パスの原則 | 「テスト・docsを除く、アプリのソースディレクトリ」。Tauriなら`src/`+`src-tauri/src/`、Python CLIなら`src/`または`*.py`、Next.jsなら`app/`+`src/`等、スタックの慣例に合わせて選ぶ |
| 判定ロジック | `git diff --cached --name-only`でステージ一覧を取得 → ソース変更の有無を判定 → **ステージ(インデックス)内容**を`git show :{manifest}`で取得し、`git show HEAD:{manifest}`(前回コミット)と比較。**作業ツリーのファイルを直接読んではならない**(「バージョンだけ書き換えて`git add`し忘れた」場合、ステージされる内容は旧バージョンのままなのに作業ツリーの新バージョンを見て誤通過するため) |
| 既知の限界 | 本チェックは**値が前回コミットと異なるか**のみを見る。意味のある増分か(対応する修正規模に見合っているか)・往復操作での回避は検出しない。それは人によるコードレビューの役割 |
| 既知のすり抜け | 通常のマージコミット(コンフリクトなし)はgit仕様上pre-commitが発火しないため対象外。ブランチ側で既にバージョンが上がっていることを人が確認する |
| amendでの挙動 | `git commit --amend`時のHEADは「これから置き換えられる対象コミット自身」を指す。そのコミットで既にバージョンを上げ済みなら、amendでソース修正を追加しても差分なしと判定されブロックされうる(既知の偽陽性)。その場合は下記の`--no-verify`で通してよい |
| 回避手段 | `git commit --no-verify`。**MUST:** 意図的にスキップする場合は、コミットメッセージに`[skip-version-check: 理由]`を含める(後から`git log --grep`で棚卸しできるようにする) |

**MUST NOT:** このフックをeslint/prettier等の既存lint-staged設定と混同しない(本フックは**バージョン整合性専用**・軽量・高速)。

### 5.1 スタック別の配置

| スタック | 配置 | 詳細 |
|----------|------|------|
| Node系(Tauri・Next.js等) | `husky` | 導入済みリポはその`.husky/pre-commit`に追加。未導入リポは`npx husky init`(`package.json`に`"prepare": "husky"`が入り、`npm install`時に他PCでも自動セットアップされる)。既存パターンは[`QUALITY_GATE_RULES.md`](../60_tooling/QUALITY_GATE_RULES.md) §3 |
| Python(`pyproject.toml`等・pre-commitフレームワーク導入済み) | `.pre-commit-config.yaml`に`repo: local`のフックを追加 | `language: system`・`entry: python scripts/check_version_bump.py`で登録(既存のruff等のhookと並列に追加)。クローン後は`pre-commit install`で有効化。既存パターンは[`QUALITY_GATE_RULES.md`](../60_tooling/QUALITY_GATE_RULES.md) §4 |
| Python(pre-commit未導入・単体スクリプト) | 素の`.git/hooks/pre-commit`は他PCに伝播しないため避け、上記のpre-commitフレームワーク(2行目)を導入してから追加する | — |

**セットアップ確認(MUST):** 新しい作業環境でクローン後、`git config core.hooksPath`が`.husky`(またはpre-commitフレームワークが設定する値)になっているか確認する。`npm install`(またはpre-commitフレームワークなら`pre-commit install`)の実行を忘れるとフックが**無警告・無痕跡で無効化**されるため、フェーズ移行直後や別PCでの作業開始時は一度確認する。

**実装例(Tauri/Node):** [`manual-studio/scripts/check-version-bump.mjs`](c:/yk-application/manual-studio/scripts/check-version-bump.mjs) — そのまま流用はできない(マニフェストのパス・形式がアプリごとに違う)が、判定ロジックのテンプレとして他アプリ導入時にコピー→パス/正規表現だけ書き換える。マニフェストが1ファイルのみ(例: `pyproject.toml`)なら上記③(一致チェック)は不要、②のみで足りる。
