加えて、次を該当するレンズに渡す（初見の第三者を除く）。
- **派生ドキュメント**: 整合性（必ず）。ほかのレンズにも該当節が要るときは渡す
- **アプリ側の画面仕様・出力仕様**（データモデルの該当節を含む）: 既存との一貫性、出力・成果物への影響、状態・境界
- **過去の決定記録**: 既存との一貫性（ほかは任意）
- **重点箇所**（差し戻し後のみ。変更した部分）: 初見を除く全レンズ
- 見つけ方は、対象ドキュメントのリンクを辿る。リンクが無い・足りないときは、同じ docs 配下の画面仕様・出力仕様・決定記録を親が検索して補い、補った資料を経緯の1周目に1行で記録する

### 初見の第三者に渡すもの

- 正本の**複製**を scratchpad に作り、そのパスを渡す。複製は**毎周、最新の本文から作り直して上書きする**。差し戻しの周も全文の複製を渡す
- 複製から除くのは、**節として分かれている**経緯・決定済み論点・承認待ち論点・実機で決める宿題の一覧の節。設計の本文と、節に混在・散在している記述は残す（決定済みと重なる所見は、棄却の規定が受ける）
- 複製のほかに渡すのは、成功の定義とスコープ外だけ（スコープ外が仮置きなら「仮」と注記する）。規約・過去の決定記録・派生ドキュメント・重点箇所は渡さない
- プロンプトに「指定した複製だけを読む。リンク切れ・参照先不明は指摘しない」と明記する（`Explore` はリポジトリ全体を探せるため、パスを渡さないだけでは隔離にならない）

## デザイン専用レンズ

| レンズ | 見るもの | 見ないもの |
|--------|----------|------------|
| **アクセシビリティ** | 構想で判定できる範囲: 設計に書かれた操作がキーボードだけで届くか、ホバー専用になっていないか、色以外の識別手段・ターゲットの大きさが書かれているか（書かれていなければ欠落） | 見た目の好み。実装でしか決まらない要件（これは「実装時チェック」に回す） |
| **状態・境界** | 状態の網羅（空・初回・上限・大量・失敗・読み込み中）。**各操作を「取り消せる / 取り消せない / 確認あり」の表にして突き合わせ、書かれていない操作や状態を「欠落」として報告する** | 個々の操作の危険度（誤操作に委ねる） |
| **誤操作** | 設計に書かれた個々の操作の危険度（押し間違い・意図しない上書き・破壊操作・クリックやドラッグの衝突・既存操作との競合） | 一覧の欠落（状態・境界に委ねる） |
| **既存との一貫性（用語・ラベル含む）** | 同じアプリ内の既存画面・規約との矛盾、用語・見出し・色・配置の揃い | 新規の発想の良し悪し |
| **タスクフロー・ウォークスルー** | 成功の定義の問いごとに「最初に見る場所はどこか、次の一手はどれか」を1手ずつ辿る | 画面の細部の見た目 |
| **出力・成果物への影響** | 書き出し結果（Word/Excel 等）のレイアウト規則の網羅（端数・区切り・空）。保存形式の移行と互換（読み込み時の変換・旧版で開いた場合・冪等性） | 画面内の見た目 |
| **整合性（ドキュメント間）** | 正本と派生の矛盾、過去の決定との食い違い、決定済み論点の蒸し返し | 新規論点の探索 |
| **前回修正の検証** | 前の周の修正が反映され、新しい矛盾を生んでいないか | 新規の論点探し |

**ビジュアル / UI デザイン**は、配置・優先度・グルーピングが読み取れるワイヤー（ASCII 可。親の仮ワイヤーを含む）があるときだけ使う。無い周は外し、他のレンズと入れ替える（見る対象が無く空振りする）。

## 周ごとの選び方

- **【converging に追加】** レンズ数は**通常3**（初見の第三者＋2）。**4以上は、機能追加型・必須レンズを回す周・前回修正の検証を足す周など必要なときだけ**。**【converging から変更】** 上限は6
- **必須レンズ**: 対象が画面を持つなら、状態・境界／誤操作／アクセシビリティ（3レンズ）を、いずれかの周で回す。構造が変わる差し戻しでは、変更に関わる必須レンズを再走させ、必須レンズの走行済みの判定をその周から数え直す（周番号は通し）

**【converging に追加】** 段階の目安（終盤は収束確認の周。全レンズが問題なしの周で収束を宣言できるなら、終盤は省いてよい）: **1周目は常に序盤**。2周目以降は、**必須レンズが走り終えており、かつ直前の周で全レンズを通して重大度「中」以上の所見（欠落を含む）が出なかった周が終盤**、それ以外が中盤。必須レンズが走り終えたあとの中盤は、前回修正の検証＋初見の第三者＋直前に指摘が出た領域の専用レンズを基本とする。

以下は**例**。同じ組み合わせの反復は、`converging-plan-reviews` の規定に従って避ける。

| 段階 | 狙い | 組み合わせの例 |
|------|------|----------------|
| 序盤 | 設計の芯 | IxD / UX（体験設計）＋ タスクフロー・ウォークスルー ＋ 第三者（初見指定） |
| 中盤 | 取りこぼし | 状態・境界 ＋ 誤操作 ＋ アクセシビリティ ＋ 第三者（初見指定） ＋ 前回修正の検証 |
| 終盤 | 収束確認 | 第三者（初見指定） ＋ 前回修正の検証 ＋ 整合性（ドキュメント間） |

画面の変更が**データモデルや出力に及ぶ機能追加**では、序盤に「出力・成果物への影響」と「既存との一貫性」を加える。

## プロンプトに足す項目

`reviewing-with-subagents` と `converging-plan-reviews` の必須項目に加えて、次を足す。各サブエージェントのプロンプトはこの順で組む。

1. レンズ名と、その「見るもの／見ないもの」、上の対応表の資料
2. 目的・利用者・成功の定義・スコープ外・実機で決める宿題を**先に**渡し、「この設計はそれを満たすか」から評価させる（初見の第三者には成功の定義とスコープ外のみ）
3. 決定済みの論点と承認待ち論点は前提として渡す（扱いは SKILL.md の Step 0。初見の第三者には渡さない）。仮置きの素案は「仮」と明示して渡し、素案の行も検証対象とする
4. 報告形式への当てはめ: 「所見」の見出しの中に、良い点（維持すべき点）を先頭に1行 → 各所見を **対象ドキュメントの引用 → 適用した規約（ファイルと節）または原則名 → 困る利用者と場面 → 重大度 → 修正案** の順で書かせる。規約が無いレンズや該当が無い所見は「原則名」か「規約外（私見）」と明記させる。状態・境界は、操作の表を「所見」の見出しの中の先頭に置かせる
5. **重大度**: 高 = 利用者が成功の定義の問いに答えられない・タスクを達成できない・**設計に書かれた**操作に確認も取り消しも無い破壊操作がある・設計に書かれた操作がキーボードだけでは届かない / 中 = 迷う・やり直しが要る・確認だけで取り消せない破壊操作がある・「欠落」（設計に書かれていない操作や状態。高にはしない） / 低 = 好み・体裁。実装でしか決まらないアクセシビリティの要件は「実装時チェック」として報告させる
