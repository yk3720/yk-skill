ひとことで言えば

Ollama（オラマ）とは、量子化した大規模言語モデルを自分の PC 上でダウンロード・実行し、http://localhost:11434 で HTTP API として提供する常駐サービスである。

クラウドの LLM API（Claude・GPT・Gemini など）と同じ「プロンプトを投げると文章が返る」インタフェースを、従量課金ゼロ・ネットワーク不要・入力データが外部に出ない形で手元に置ける。代わりに、モデルの重みを自分のマシンのメモリに載せて自分の CPU / GPU で推論するため、ハードウェアの制約を受け、品質と速度は載せられるモデルサイズで決まる。

カバーする範囲

モデル配布・量子化・GPU 割り当て・ローカル REST API

カバーしない範囲

モデルそのものの学習・分散推論・フロンティア級の品質

競合

LM Studio・llama.cpp 直・vLLM・Jan・GPT4All

なぜ生まれたのか

2023 年に Meta の LLaMA の重みが公開され、続いて Georgi Gerganov 氏の llama.cpp が「GPU が無くても C++ と量子化で LLM を動かせる」ことを実証した。しかし当時の実行手順は、モデルの重みを HuggingFace から探してきて、GGUF に変換し、量子化レベルを選び、プロンプトテンプレートを手で組み立て、CLI の引数を大量に渡す、というものだった。「動かせる」と「気軽に使える」の間に深い溝があった。

Ollama はこの溝を埋めるために作られた。やったことは Docker が「コンテナ」に対してやったことと同じ発想である。

  • モデルをレジストリ配布に — ollama pull qwen2.5:7b だけで、正しい量子化・正しいプロンプトテンプレート・正しいパラメータがセットで落ちてくる（docker pull の LLM 版）。
  • 実行をデーモン + API に — バックグラウンドで ollama serve が常駐し、複数のアプリが localhost の HTTP で共有できる。モデルのロード / アンロード / VRAM 割り当てはデーモンが面倒を見る。
  • インタフェースを OpenAI 互換に — 既存のクラウド API 用コードの base_url を差し替えるだけでローカルに切り替えられる。

背景にある需要は明確だ。プライバシー（社内文書・コード・個人情報を外部 API に送りたくない）、コスト（大量処理を従量課金でやると高い）、オフライン / 低レイテンシ（回線に依存したくない、往復遅延を消したい）、再現性（モデルのバージョンが勝手に変わらない）。

まず理解する3つ

これだけ分かれば評価に入れる

1
Ollama は「実行環境」であって「モデル」ではない必須

賢さを決めるのは中に入れるモデル（Qwen2.5・Llama 3.x・Gemma・Phi 等）と、その量子化レベル。Ollama 自体は配布・ロード・API 化を担う土台。DBMS（PostgreSQL エンジン）と、そこに入れるデータ / スキーマの関係に近い。

2
常駐デーモンに localhost の HTTP で話す必須

ollama serve が 127.0.0.1:11434 で待ち受ける。アプリ側はライブラリを埋め込むのではなく、ローカルの Web サーバーに JSON を POST する。ローカルの Redis や Postgres に繋ぐのと構造は同じ。

3
性能はメモリと量子化のトレードオフで決まる推奨

モデルの重みは丸ごと RAM（GPU があれば VRAM）に載る。7〜8B のモデルを Q4_K_M 量子化で約 5〜6 GB。載れば動く、載らなければ極端に遅くなるか起動しない。「大きいモデルを雑に量子化」より「小さいモデルを素直に量子化」の方が結果は良い。

仕組みとアーキテクチャ

下から順に積み上がっている

レイヤ構成

Ollama は薄いラッパーで、実際の数値計算は下層の llama.cpp（および新しい社内エンジン）が担う。上から見ると次のようになっている。

アプリ層Toolkit.exe / スクリプト / CLI — HTTP クライアント
API 層ollama serve — :11434 で REST を提供。ネイティブ /api/* と OpenAI 互換 /v1/* の 2 系統
オーケストレーション層モデルのロード / アンロード（keep-alive）・GPU/CPU への割り当て・プロンプトテンプレートの適用・並列リクエストのキューイング
推論エンジン層llama.cpp（GGML）ほか — 量子化テンソルの行列演算、KV キャッシュ管理、CUDA / Metal / ROCm / AVX への振り分け
モデル層GGUF ファイル（重み + メタデータ + トークナイザ）— ~/.ollama/models にレジストリ形式で保存
用語: GGUF（GPT-Generated Unified Format）

llama.cpp が使う単一ファイルのモデル形式。重みテンソル・量子化情報・トークナイザ・プロンプトテンプレート・ハイパーパラメータを 1 つの .gguf にまとめる。実行ファイルにおける単一バイナリ（static link 済み exe）と同じ発想で、これ 1 つ配れば依存を解決せずに動く。前身の GGML 形式を置き換えた。

用語: 量子化（Quantization）

モデルの重み（本来 16 bit 浮動小数）を、4 bit などの低ビット整数 + スケール係数で近似し、メモリと計算量を削る手法。音声を FLAC（可逆）から 320 kbps MP3、128 kbps MP3 と圧縮していくのに似ている — ファイルは小さくなり、ある所までは違いが分からず、やり過ぎると明確に劣化する。

  • Q8_0: 8 bit。ほぼ無劣化。サイズは元の約 1/2
  • Q4_K_M: 4 bit（K-quant, medium）。Ollama の既定で実用上の標準。サイズは元の約 1/4、品質低下はわずか
  • Q3_K / Q2_K: 3〜2 bit。極端に小さいがハルシネーション・破綻が増える。基本は使わない

経験則: 「一段大きいモデルを Q3」より「一段小さいモデルを Q4_K_M」の方が実用品質は上。

推論のとき何が起きているか

たとえ: レストランのセントラルキッチン vs 出前

クラウド API = 出前。注文（プロンプト）を電話で伝える。速くて美味い（フロンティア級モデル）が、注文内容は店に伝わるし、頼むたびに代金がかかり、回線が切れたら注文できない。

Ollama = 自宅のキッチン。材料（モデルの重み）を一度買って冷蔵庫（ディスク）に入れ、使うときに調理台（RAM / VRAM）に広げる。作るのは自分の火力（CPU / GPU）次第で、プロの味には届かないこともあるが、何を作ったかは誰にも伝わらず、材料費以外はかからず、停電しなければいつでも作れる。

  • 買い物（ollama pull）→ ディスクに GGUF を保存
  • 調理台に広げる（初回リクエスト）→ 重みを RAM/VRAM にロード（数秒〜数十秒）
  • 調理（生成）→ 1 トークンずつ計算。速度は tokens/sec で測る
  • 片付け（keep-alive 期限切れ）→ 一定時間使わないとメモリから降ろす（既定 5 分）
用語: コンテキスト長 / KV キャッシュ

コンテキスト長は、モデルが 1 回の推論で参照できるトークン数の上限（例: 8K / 32K / 128K）。会話や文書が長いほど、KV キャッシュ（Key-Value cache）という中間状態が VRAM を食う。重みが載っても「重み + KV キャッシュ + 実行時オーバーヘッド」で溢れることがある。ページングを起こしたときの OS のスワップ地獄と同じで、溢れた瞬間に体感速度が桁で落ちる。Ollama では num_ctx パラメータで上限を指定する。

toolkit 固有の注意: スレッド

toolkit の掟は「COM 操作もジョブも UI スレッドで同期実行」。LLM 呼び出しは数秒〜数十秒ブロックするので、これを ctx.submit の同期ジョブに素直に入れると窓が固まる。LLM 呼び出しだけワーカースレッドに逃がす（Office COM は UI スレッドのまま）か、ストリーミングで受けて after() でチャンクを UI に流す。Word/Excel の COM とネットワーク I/O を混同しないこと。

API の使い分け

エンドポイント用途選ぶ理由
/api/chat複数ターンの会話（role 付き messages）Ollama ネイティブ。options で num_ctx 等を細かく渡せる。tool calling もここ
/api/generate単発のプロンプト → 補完（1 ターン）要約・言い換えなど「1 回投げて 1 回返す」タスク。system と prompt だけで済む
/v1/chat/completionsOpenAI SDK 互換クラウドと同じコードで base_url だけ差し替えたいとき。将来 Claude / OpenAI に切り替える余地を残せる
/api/embeddings文をベクトルに変換用語集の類似検索・重複検出など。生成とは別モデル（nomic-embed-text 等）
/api/tags導入済みモデルの一覧起動チェックと「モデルが入っているか」の確認に使う

コード例 1: 最小の呼び出し（curl）

このコードがやること: 導入済みの qwen2.5:7b に敬語化を頼み、ストリーミングを切って一括で JSON を受け取る。

# stream:false で 1 回のレスポンスにまとめる curl http://localhost:11434/api/chat -d '{ "model": "qwen2.5:7b", "stream": false, "messages": [ {"role":"system", "content":"入力を丁寧なビジネス敬語に直す。意味は変えない。"}, {"role":"user", "content":"明日までに資料送って"} ], "options": { "temperature": 0.2, "num_ctx": 4096 } }'

コード例 2: toolkit 側（httpx・非ストリーム）

このコードがやること: app/core/ai/ に置く想定の薄いクライアント。タイムアウトを長めに取り、Ollama 未起動なら分かりやすい例外に変換する。

import httpx OLLAMA = "http://127.0.0.1:11434" class OllamaNotRunning(RuntimeError): ... def is_up() -> bool: try: return httpx.get(f"{OLLAMA}/api/tags", timeout=1.5).status_code == 200 except httpx.HTTPError: return False def complete(system: str, user: str, model="qwen2.5:7b") -> str: if not is_up(): raise OllamaNotRunning( "Ollama が起動していません。`ollama serve` を実行し、" "`ollama pull qwen2.5:7b` でモデルを導入してください。") r = httpx.post(f"{OLLAMA}/api/chat", timeout=120, json={ "model": model, "stream": False, "messages": [ {"role": "system", "content": system}, {"role": "user", "content": user}, ], "options": {"temperature": 0.2, "num_ctx": 4096}, }) r.raise_for_status() return r.json()["message"]["content"].strip()

この complete() を UI スレッドから直接呼ばない。threading.Thread で走らせ、結果を queue 経由で受けて after() で UI に反映する。

コード例 3: OpenAI 互換で書いておく

このコードがやること: 公式 openai ライブラリをそのまま使い、base_url をローカルに向ける。将来クラウドへ切り替えるとき、この 2 行だけ変えればよい。

from openai import OpenAI client = OpenAI(base_url="http://127.0.0.1:11434/v1", api_key="ollama") # キーはダミーで可 res = client.chat.completions.create( model="qwen2.5:7b", messages=[{"role":"user","content":"この表の列名を英語に直して"}], temperature=0.2, ) print(res.choices[0].message.content)
たとえ: プリンタスプーラ / OS のサービス

ollama serve は Windows のサービス（プリンタスプーラや Windows Update）と同じ「常駐して要求を待つ」プロセス。サービスが止まっていればジョブを投げても Connection refused で即エラーになる。toolkit の flowchart-excel launcher が「exe を見つけられなければ解決手順つきメッセージで止まる」のと全く同じで、「未起動・モデル未導入」を握って、ユーザーに次の一手（ollama serve / ollama pull）を示すのが正しい振る舞い。

モデル選び

「入るサイズ」から逆算する

選定の順番は「タスク → 必要な賢さ → 手元のメモリに載る最大サイズ → その中でタスクに強いモデル → 量子化 Q4_K_M」。toolkit の用途（敬語化・要約・表記提案・用語抽出）は難関タスクではないので、7〜8B クラスで十分実用になることが多い。

モデル（Ollama タグ例）パラメータQ4_K_M サイズ目安必要メモリ目安
(重み+文脈+余裕)		向き
phi3.5 / phi4-mini3.8B約 2.5 GB約 5 GB最軽量。短い整形・分類。CPU のみでも実用速度
qwen2.5:7b7.6B約 4.7 GB約 8 GB日本語・指示追従が強い。toolkit のデフォルト候補。JSON 出力・tool calling 対応
llama3.1:8b8.0B約 4.9 GB約 8 GB汎用のバランス型。英語寄り。エコシステムの資料が豊富
gemma2:9b9.2B約 5.8 GB約 9〜10 GB要約・言い換えが自然。やや重い
qwen2.5:14b14.8B約 9 GB約 13〜14 GB品質を一段上げたいとき。16 GB VRAM か 32 GB RAM が目安
nomic-embed-text0.14B約 0.3 GB約 1 GB生成ではなく埋め込み専用。類似検索・重複検出用に併用

※ サイズ・所要メモリは目安。量子化ビルドやコンテキスト長で前後する。実際の VRAM 使用は ollama ps で確認できる。

GPU なし / RAM 16 GB

phi4-mini か qwen2.5:7b。CPU 推論は 5〜15 tokens/sec 程度。短文タスク向き

VRAM 8 GB（RTX 4060 等）

qwen2.5:7b / llama3.1:8b が快適。30〜60 tokens/sec。toolkit の標準想定

VRAM 16〜24 GB

qwen2.5:14b、余裕があれば 32B クラス。品質はクラウドの中位に近づく

用語: Modelfile

FROM qwen2.5:7b のように既存モデルを起点に、SYSTEM プロンプト・PARAMETER temperature 0.2・停止トークンなどを固定した派生モデルを定義するテキストファイル。Dockerfile の LLM 版。toolkit なら「表記チェック用」「敬語化用」といったタスク特化のプリセットを Modelfile で作り、ollama create toolkit-keigo -f Modelfile で名前を付けて配れる。プロンプトをコード外に出せる。

初心者がはまりやすい落とし穴

評価前に知っておくと時間を節約できる

「小さいモデルでも GPT-4 級だろう」という期待値のズレ

7〜8B はフロンティアモデルの数十分の一の規模。込み入った推論・長文の一貫性・マイナー知識では明確に劣る。回避策: タスクを「整形・分類・要約・抽出」など判断の幅が狭いものに絞る。creative な生成や難しい判断はクラウドに回す設計にする。

初回リクエストだけ異様に遅い / タイムアウトする

モデルを RAM/VRAM にロードする時間（数秒〜数十秒）が最初の 1 回に乗る。回避策: HTTP クライアントのタイムアウトを 120 秒以上に。起動時に keep_alive を長めにした空リクエストでウォームアップしておく。既定では 5 分無操作でアンロードされ、次でまた遅くなる。

コンテキストを増やしたら急に遅く・不安定になった

num_ctx を大きくすると KV キャッシュが VRAM を食い、閾値を超えた瞬間に CPU へこぼれて体感が桁で落ちる。回避策: タスクに必要な最小の num_ctx（4K〜8K）にする。長文は要約してから渡す。ollama ps で「100% GPU」から落ちていないか確認。

Q2 まで量子化して「使い物にならない」と結論する

2〜3 bit 量子化は破綻・ハルシネーションが顕著。回避策: 迷わず Q4_K_M（Ollama 既定）。それで載らないなら 1 段小さいモデルへ。「大きいモデルの過剰量子化」は避ける。

exe にモデルや Ollama を同梱しようとする

モデルは数 GB、Ollama 本体も別インストーラ。PyInstaller の onefile に入れるものではない。回避策: flowchart-excel launcher と同じく「外部プロセスに接続するだけ」。Ollama の導入とモデルの pull はユーザー手順（または初回セットアップ bat）にし、アプリは localhost:11434 の有無を検出するだけにする。

CPU 推論を GPU 推論と同じ速度で見積もる

GPU なしだと 7B で数〜十数 tokens/sec。300 字の敬語化に十数秒かかることもある。回避策: UI を非同期に（進捗表示・キャンセル可能に）。短文タスクに限定するか、GPU 前提と割り切る。

料金・ライセンス

Ollama は無料。注意点はモデル側にある

  • Ollama 本体: オープンソース（MIT ライセンス）。無料。従量課金なし。商用利用可。
  • 推論コスト: 電気代のみ。API 課金・トークン課金は一切ない。オフラインで完結。
  • モデルのライセンスは個別: Ollama で配られるモデルはそれぞれライセンスが違う。Apache-2.0 / MIT（Qwen の一部・Mistral 系）は商用も自由。Llama 系は Meta 独自ライセンス（月間アクティブユーザー 7 億超の制限、出力で他モデルを学習させない条項など）。Gemma は Google の利用規約。業務ツールに組み込むなら、採用モデルのライセンス条文を確認する。
  • Ollama Cloud / Turbo: 同じ CLI・API のままクラウド GPU で大型モデルを動かす有料オプションもある（ローカルで動かない規模のモデル用）。ローカル運用だけなら無関係。

クラウド API とのコスト比較（イメージ）

1 日 200 リクエスト・平均 800 トークン入出力を 1 年続けた場合 —— クラウド（安いモデルでも）で年 数千円〜、Ollama ローカルなら追加ハード費を除けば ほぼ電気代のみ。ただし GPU を新規購入するなら初期数万円。低頻度なら差は小さく、選定理由はコストより「データを外に出さない」になることが多い。

長所と短所（toolkit の文脈で）

向いている

  • 業務文書が外に出ない — Word/Excel の中身を第三者 API に送らずに済む
  • 従量課金ゼロ — 何回叩いてもコストが増えない。バッチ処理に強い
  • オフライン — 回線・VPN・プロキシに依存しない
  • 再現性 — モデルのバージョンが勝手に変わらない
  • 切替可能な設計にしやすい — OpenAI 互換なので後からクラウドへ差し替えられる

向いていない / 弱点

  • 品質の天井 — 難しい判断・長文の一貫性はフロンティア級に届かない
  • ハードウェア依存 — GPU が無いと遅い。VRAM が足りないと動かない
  • 配布が増える — ユーザー各自が Ollama 導入 + モデル pull（数 GB）
  • 初回ロード遅延 — 使い始めとアンロード後に待ちが入る
  • 運用の当事者になる — モデル更新・VRAM 管理・障害切り分けが自分の仕事になる

実務的な落としどころ: 「表記ゆれの提案」「選択範囲の敬語化・要約」など判断の幅が狭いタスクを Ollama ローカルで賄い、app/core/ai/ の裏側を OpenAI 互換の I/F にしておく。品質が要る場面が出てきたら、その I/F の実装を Claude Haiku 4.5 に差し替えるだけで済む。

専門用語集

この分野で繰り返し出てくる語

LLM（Large Language Model：大規模言語モデル）
大量のテキストで学習し、次のトークンを確率的に予測するニューラルネットワーク。→ 推論、トークン
推論（Inference）
学習済みモデルに入力を与えて出力を得る処理。学習（training）と対。Ollama がやるのはこちらだけ。
トークン（Token）
モデルが扱う最小単位。日本語なら 1〜2 文字前後で 1 トークンのことが多い。課金も速度も文脈長もトークンで数える。
llama.cpp
C/C++ 製の推論エンジン。CPU・各種 GPU で量子化モデルを動かす。Ollama の下層。→ GGUF
GGUF
llama.cpp のモデルファイル形式。重み・トークナイザ・テンプレートを 1 ファイルに同梱。→ 量子化
量子化（Quantization）
重みを低ビットで近似してサイズと計算量を削る。Q4_K_M が実用標準。→ VRAM
コンテキスト長（Context length / num_ctx）
1 回の推論で参照できるトークン上限。長いほど KV キャッシュがメモリを食う。
KV キャッシュ（Key-Value cache）
既に処理したトークンの中間状態。再計算を避けるための VRAM 常駐データ。文脈が長いほど増える。
keep-alive
推論後、モデルをメモリに保持しておく時間（既定 5 分）。切れると次回ロードで待ちが発生。
Modelfile
既存モデル + system プロンプト + パラメータを固定した派生モデル定義。Dockerfile の LLM 版。
埋め込み（Embedding）
文を固定長ベクトルに変換したもの。類似度計算・検索・重複検出に使う。生成モデルとは別モデル。
tool calling / function calling
モデルが「この関数をこの引数で呼べ」という構造化 JSON を返す機能。Ollama も対応モデルで利用可。
VRAM / RAM
GPU メモリ / メインメモリ。モデルの重みと KV キャッシュがここに載る。載る量が性能を決める。
ストリーミング（SSE：Server-Sent Events）
生成トークンを 1 つずつ push で受け取る方式。"stream": true。体感速度と途中キャンセルのために使う。

次に学ぶと良いもの

この知識を起点に広げる

llama.cpp と GGUF の内部
Ollama の下で何が起きているか。量子化スキームや GPU offload の仕組みが分かると VRAM 見積もりが正確になる
構造化出力（JSON mode / grammar 制約）
「表記ゆれの候補を配列で返す」など、ツール組み込みでは出力形式の固定がほぼ必須になる
RAG（検索拡張生成）と埋め込み
用語集や過去文書を根拠にさせたいときの定石。nomic-embed-text + ベクトル検索が入口
クラウド LLM API の設計（Claude / OpenAI）
品質が要る経路の受け皿。OpenAI 互換 I/F を挟んでおけばローカルと共存できる
LM Studio / vLLM / llamafile
同じローカル推論の別アプローチ。GUI 重視・スループット重視・単一実行ファイル配布と、目的で選択肢が分かれる
量子化の評価指標（perplexity・KL divergence）
「Q4 でどれだけ劣化したか」を数値で語れると、モデル選定が主観から抜けられる
