# Converging Plan Reviews

計画・設計ドキュメント(grill-meの結果や既存の仕様書)に対し、`reviewing-with-subagents`の1周レビューを土台に、**視点をローテーションしながら**繰り返し実施し、指摘が出なくなるまで磨き込む。

## 前提

- 対象は**ファイルとして存在するドキュメント**であること。サブエージェントは会話を見られないため、対話だけで固めた設計はまず1つのMarkdownファイルに書き出してからループに入る
- **対象が複数ファイル（本体＋依存ドキュメント等）に分かれる場合**、各サブエージェントには関連ファイルの**パスをすべて**渡し、ファイル間の整合性・リンク先の正しさも確認対象に含めるよう指示する
- **対象が本スキル自身または直接の依存スキル（自己適用）の場合**、各サブエージェントへの指示に「あなたが従っている手順自体が評価対象であり、手順への遵守を理由に欠陥を見逃さないこと」を明記する（確認バイアス・手続き遵守バイアスを防ぐ）
- 1周ごとの並列サブエージェント起動の手順・出力形式は`reviewing-with-subagents`のSSOT(`SKILL.md`・[references/perspectives.md](../reviewing-with-subagents/references/perspectives.md))に従う。本スキルはそこに**ループ・収束判定・視点ローテーション**を足すもの

## ワークフロー

### Step 1: 対象確定
ドキュメントのパスを確認する。まだファイル化されていなければ、ループに入る前にまず書き出す。

**ロードマップの有無を確認する**: 「何を・どの順で・どこまでやったら完了か」(フェーズ/マイルストーン単位)が書かれているか確認する。無ければ、レビューループに入る前にまず素案として追記する(詳細なタスク分解までは不要。粒度・タスク単位への分解が別途必要なら、ユーザーに確認のうえ作成する)。ロードマップが無いままレビューを繰り返すと、指摘が「実装順序」の論点に集中せず発散しやすい。**対象がフェーズ構造を持つ計画ではない場合**（運用手順書・スキル定義・ルール文書等、実行時の分岐・判断基準の集合であって完了基準を持たないもの）は、この確認・追記は適用しない。

### Step 2: 1周実施

1. **視点の選定(毎周ローテーション・MUST)**: perspectives.mdのレンズ、またはこのドキュメント固有のカスタムレンズから3つ以上選ぶ。**過去の周と同じレンズの組み合わせを繰り返さない**。目安の配分:
   - 序盤の周: ドキュメントの性質に合った実質的な観点(データ設計・プライバシー / 技術実現性 / 運用・保守性 など)
   - 中盤以降の周: 「前回までの修正が本当に反映され、新たな矛盾を生んでいないか」を検証するレンズを最低1つ含める
   - 各周に、過去の指摘に一切引きずられず**今初めて読む第三者**として通読するレンズを最低1つ含める
   - **カタログのレンズが実質的に尽きた場合**: 既存レンズの単純な差し替えで字面だけ新しい組み合わせを作らない。対象ドキュメント固有のカスタムレンズ（例: 特定セクションへの深掘り、特定ステークホルダー視点）を優先して作る
2. `reviewing-with-subagents`の手順で3体以上を並列起動する。各サブエージェントには**ドキュメントを直接Readさせる**(貼り付けでなくパスを渡す)
3. 各サブエージェントへの指示に、**「重大度が中以上の指摘がなければ素直に『重大な問題なし』と書く」**旨を必ず含める(指摘を無理に捻り出させない)

### Step 3: 統合・反映

- 技術的な矛盾・ドキュメント整合性の指摘は直接ドキュメントに反映する
- **ユーザーの価値観・優先順位次第の判断(ポリシー選択)**は、直接決めずAskUserQuestionで確認してから反映する(推奨案を添える)。**技術的矛盾かポリシー選択か判定に迷う場合は、ポリシー選択側に倒す**(上記の通りAskUserQuestionで確認する。ユーザーが明示していない前提を無断で固定するリスクの方が、確認の手間より大きいため)
- 対象ドキュメントに見出し `## レビューの経緯` を用意し(無ければ追記)、その周で見つかった指摘と対応を1行ずつ追記する。書式: `- {周番号}周目({レンズ名}): {指摘要約} → {対応}`
  - 決定の本文は該当節に書き、経緯欄は要約とリンクに留める
  - **対象が運用手順書・スキル定義等でこの節を持たせるのが不自然な場合**は追記せず、チャットの完了報告のみで経緯を伝える

### Step 4: 収束判定

- **その周に使ったレンズのうち過半数（最低2つ）が「重大な問題なし」(または相当する明確な合格宣言)を出したら収束**とみなし、ループを終了する（3レンズなら2/3、4レンズなら3/4、5レンズなら3/5）
- 収束していなければStep 2に戻り、**まだ使っていない角度のレンズ**で次の周を回す
- **上限**: 8周を目安の上限とする。8周を超えても収束しない場合はループを止め、残る論点を要約してユーザーに判断を委ねる(無限ループにしない)。ユーザーの回答が得られたら、(i) 方針を固定してStep 5の完了報告に進む、または (ii) 残論点を絞って1周だけ追加で回す、のいずれかを**AskUserQuestionで**選んでもらう

**例**: 1周目「データ設計・プライバシー / 技術実現性 / 運用・保守性」→ 指摘を反映 → 2周目「技術的整合性の再検証 / プライバシー最終チェック / ドキュメント整合性」(1周目の対応が本当に十分か検証) → まだ指摘あり反映 → 3周目「新規変更の妥当性 / 実装詳細のセキュリティ / フレッシュな全体俯瞰」→ 3レンズ中2つが「重大な問題なし」で収束

### Step 5: 完了報告

収束したら、周回数・主な発見・最終状態を簡潔に報告する。`## レビューの経緯` 節を追記した場合はそこを参照させ、チャットに全文を再掲しない(節を持たせなかった場合はチャットの報告が経緯の正)。

## 依存

- `reviewing-with-subagents` — 1周の並列サブエージェント起動プロトコル(SSOT)
- `grill-me` — レビュー対象の計画をまだ壁打ちで固めていない場合の前段(任意)

## やらない

- コード実装そのもの(本スキルは計画・設計ドキュメントの磨き込みに限る)
- 1周だけのレビュー(→ `reviewing-with-subagents`をそのまま使う)
- ポリシー判断の代行(必ずユーザーに確認する)
